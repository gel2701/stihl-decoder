# STIHL Official Product Harvester

This pipeline imports current product information from the official STIHL Brazil store into an isolated candidate dataset for review.

## Safety model

The harvester is intentionally separated from the canonical STIHLDecoder data stores.

It may write only below:

`data/candidates/`

It does **not** write to:

- `data/stihl_database.json`
- `data/public_evidence_facts.json`
- `data/public_evidence_baseline_manifest.json`

Every harvested product is marked:

- `promotion_status: CANDIDATE_REVIEW_REQUIRED`
- `display_eligible: false`
- `single_value_eligible: false`
- `market: BR`

This preserves market-specific distinctions and prevents Brazilian specifications from silently replacing European, US or historical STIHL data.

## Source

Primary catalog source:

`https://loja.stihl.com.br`

Catalog discovery uses the public VTEX product search endpoint. Product-page enrichment is optional and can collect manual links and a page hash for provenance.

## Commands

Dry run, no file writes:

```bash
npm run harvest:stihl-br:dry
```

Write the candidate store:

```bash
npm run harvest:stihl-br
```

Write candidates and enrich each product page for manual links:

```bash
node scripts/stihl_official_harvester.js --write --enrich-pages
```

Limit the run during development:

```bash
node scripts/stihl_official_harvester.js --max=10
```

Run the isolated test suite:

```bash
npm run test:stihl-harvester
```

## Candidate schema

The generated store uses `stihl-official-candidate-v1` and contains source provenance, retrieval time, source payload hashes, product reference, normalized model identity, raw specifications, mapped canonical specification candidates, image URLs and optional manual URLs.

Examples of normalized fields include:

- `displacement_cc`
- `power_kw`
- `weight_kg`
- `fuel_tank_l`
- `oil_tank_l`
- `sound_pressure_db`
- `sound_power_db`
- `vibration_left_m_s2`
- `vibration_right_m_s2`
- `guide_bar_cm`
- `chain_pitch`
- `chain_model`

## Review phase

`src/utils/officialCandidateReview.js` compares candidate specifications with the current canonical model database and public evidence store without writing to either source.

A candidate field is classified as one of the following:

- `MATCH_CANONICAL`
- `CANONICAL_MATCH_EVIDENCE_CONFLICT`
- `CONFLICT_CANONICAL`
- `NEW_FIELD_CANDIDATE`
- `CORROBORATES_PUBLIC_EVIDENCE`
- `CONFLICT_PUBLIC_EVIDENCE`
- `MODEL_NOT_FOUND`

Evidence suggestions generated by the review layer remain non-displayable and require a separate approved promotion step before they can become public evidence.

## Promotion policy

There is deliberately no automatic promotion command in this phase.

Promotion into `public_evidence_facts.json` or `stihl_database.json` must remain a separate reviewed operation that:

1. confirms the exact STIHL model identity;
2. preserves the market (`BR`) and configuration context;
3. checks conflicts against existing official documents;
4. updates the approved evidence baseline when applicable;
5. passes the existing immutable-evidence regression tests.
